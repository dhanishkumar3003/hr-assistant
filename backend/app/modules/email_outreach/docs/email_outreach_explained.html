The big picture

Read this part first — everything else is a zoom-in on one piece of it.

This module's whole job is: get an email in front of a candidate, but never without a human saying "yes, send it" first — then figure out what the candidate said back.

Every email this module sends goes through the same four-stage life cycle. Nothing skips a stage. A row in the database tracks exactly which stage each candidate's email is in right now:

Draft → Approved → Sent → Inactive (if nobody replies in time)

A draft is text sitting in the database that hasn't gone anywhere yet — HR can still read it and change it. Once HR approves it, it's locked in as "ready to go" but still hasn't been emailed. The actual send is a separate step: only then does it become sent, with a real tracking token attached so a reply can be matched back to it later. If the candidate never replies within the configured time window, a cleanup job flips it to inactive automatically — nobody has to remember to do that by hand.

Separately from all of that, there's a second flow: reading what candidates write back. A background listener starts automatically the moment the backend server boots — no separate process to run — and Gmail pushes a notification the instant a reply lands, instead of the module having to go check. A webhook door exists too, for providers that push replies directly. Either way, the reply text gets fed to a classifier that decides: interested, declined, or needs a human to look at it.

Rounds, not "purpose"

The other big idea this module is built around, alongside the four-stage life cycle above.

Every email this module can send — the initial interview invite, a technical assessment, a next-round invite, a rejection — is just an entry in one shared rounds catalog. The invitation itself isn't numbered — it's an acceptance gate, not an interview round — so numbering starts once a candidate is actually being interviewed: round 1 is a technical assessment, round 2 is a next-round invite. Rejection is also unnumbered, a terminal outcome rather than a step in the sequence. Tracking "what stage is this candidate at" is the same question as "which round are they on" — one number, not four separate concepts.

round_idround_numberround_typeWhat it does
ROUND-1nullinvitationGoes through /email/draft → approve → send. Uses interview_call.html. Accept/decline gate — not counted as an interview round.
ROUND-2-BACKEND1assessmentGoes straight out through /email/test-round — no draft/approval step. Uses email_round_test.html.
ROUND-32next_roundSame draft/approve/send path as the invitation, different subject line.
ROUND-REJECTEDnullrejectionDraft/approve/send path, LLM-written wording, candidate_rejection.html. Not part of the numbered sequence.

The catalog itself lives in app/tests/modules/email_outreach/testdata.json's rounds[] array today (see candidate_source.py). Every route that touches a round only ever takes a round_id — never a job description, a duration, a question count. The server looks all of that up itself.

Where the round lives on a candidate

The email_outreach_emails table has two columns for this: round_id and round_number. Drafting the invite writes them at creation time (round_number stays null until a real interview round starts); a successful /email/test-round send updates them on the candidate's existing row afterward (test-round doesn't create a new row — it emails against whichever row is already Sent). GET /email/status/{candidate_id} always reflects whichever round is current.

assessment rounds don't go through /email/draft

Passing an assessment-typed round_id to POST /email/draft gets rejected with a 422 — those rounds have no HR-approval step by design, they're emailed directly via POST /email/test-round.

Why so many small files?

Each file answers exactly one question. If you need to change how an email is worded, you're in email_builder.py or a template. If you need to change how a reply is matched to a candidate, you're in reply_matcher.py — and nowhere else. Splitting things this way means changing one behavior never risks breaking an unrelated one.

Step 1

Drafting an email

Someone (or something) asks: "write an outreach email for this candidate."

POST /email/draft
{
  "candidate_id": "CAND-001",
  "round_id": "ROUND-1"
}

That's the whole request body. This lands in api.py, which hands it straight to EmailDrafter.create_draft() in drafter.py. Nothing else is caller-supplied — the candidate's email/name, the job/HR details their record points to, and the round's name/type/number are all looked up server-side via candidate_source.py. That function does four things, in order:

  1. Checks the database — is there already a pending draft for this candidate? If so, it refuses (you can't have two drafts fighting over one candidate).
  2. Looks up round_id in the rounds catalog (see Rounds, not "purpose") and reads its round_type. An assessment round is refused with a 422 — those go through POST /email/test-round instead.
  3. Picks the right template based on round_type: an invitation and a next_round both use the same HTML template (interview_call.html) with a different subject line, while rejection uses its own template and calls rejection_drafter.py first to get an LLM-written paragraph — see the callout below.
  4. Saves the result to the email_outreach_emails table with status Draft, along with round_id/round_number for tracking. Nothing has been sent. Nobody outside your own database can see this yet.

Where the rejection wording comes from

rejection_drafter.py sends a short prompt to a local LLM (via Ollama) asking for 2–3 sentences: thank the candidate, say the company won't move forward, keep it warm and non-specific. If Ollama is down or errors out, it falls back to a fixed, pre-written paragraph instead — drafting a rejection should never fail just because an AI model happened to be offline.

Why is the token missing at this point?

Every sent email carries a tracking token embedded in its subject line (like [Ref:a1b2c3d4]), which is how a reply later gets matched back to the right candidate. But a draft might get edited or rejected before it's ever sent — so generating that token now would be wasted work. It's created fresh at the moment of actually sending (Step 3), never before.

Step 2

HR approves (or rejects) it

The human checkpoint. Nothing reaches a candidate's inbox without this.

POST /email/approve
{
  "candidate_id": "CAND-001",
  "approved_by_hr_id": "HR-001",
  "edited_body": null
}

Handled by approval_gate.py. It looks up the pending draft for that candidate; if it's not sitting in Draft status, it refuses outright — you can't approve something that was already sent, or that doesn't exist.

approved_by_hr_id is looked up against the same HR catalog candidate_source.py uses everywhere else — the resolved name (not the raw id) is what actually gets stored in approved_by, so status/history views stay human-readable. An unknown hr_id is rejected with a 404.

If HR wants to change the wording before approving, they pass the new HTML in edited_body and that replaces the drafted text entirely — whatever HR approves is exactly what goes out later, with no re-generation in between. The row flips to Approved and records who approved it and when.

Rejecting works the same way through POST /email/reject — the draft moves to Rejected and is permanently done; it can never be sent.

Step 3

Sending it

The moment the email actually leaves the building.

POST /email/send
{ "candidate_id": "CAND-001" }

This calls EmailSenderService.send_approved_draft() in sender.py, which is the only place these five things happen together:

  1. Confirms the draft is actually Approved — refuses otherwise.
  2. Generates the real tracking token now, and appends it to the subject: "Interview Invitation [Ref:a1b2c3d4]".
  3. Wraps the approved body into a real email message via email_builder.py — this also sets a unique Message-ID header and a "plus-tagged" reply address like yourinbox+CAND-001@gmail.com, both of which matter later.
  4. Hands that message to whichever backend is configured (email_backend.py picks one — see the box below) and asks it to send.
  5. On success, records the send time and computes a response deadline (send time + the configured threshold, default 72 hours), then flips the row to Sent.

Two interchangeable ways to actually send

email_backend.py is a single switch controlled by one setting (email_backend). Every option below exposes the same interface, so nothing else in the codebase needs to know or care which one is active. IMAP/SMTP and Gmail-API polling used to be options here too — both were removed once the Pub/Sub push listener covered the same ground with no polling delay (see Step 4).

Step 4

Reading a candidate's reply

Two doors in, one hallway once you're inside.

A reply can arrive two different ways, but both end up calling the exact same function — ReplyTrackerService.process_reply() in reply_tracker.py — so the actual handling logic is written once, not twice.

Background listener (auto-started) ↘
POST /email/webhook/reply ↗ → process_reply()

Door 1 — the background listener, started for you

app/main.py starts a daemon thread the moment the FastAPI server boots — nothing to run separately, no CLI command to remember. That thread calls ReplyTrackerService.monitor_forever(), which registers a Gmail watch() and opens a live Pub/Sub streaming pull: Gmail pushes a notification the instant the inbox changes, a background thread resolves it to the actual new message, and it's handed to process_reply() within seconds — no fixed polling interval to wait out. The watch registration expires after 7 days (Gmail's own limit), so the loop quietly re-registers it once a day on its own.

Whatever backend the reply came through, each candidate message gets passed to reply_matcher.py, which tries three signals, in order, to figure out which candidate it's from:

  1. Message threading — does this email's "In-Reply-To" header point at the Message-ID we sent? Most reliable, since every mail client sets this automatically.
  2. The plus-tag — was it sent to yourinbox+CAND-001@...? Survives even if threading headers get stripped somewhere along the way.
  3. The subject token — does the subject still contain [Ref:a1b2c3d4]? Last resort, since a forwarded original invite could carry the same token without being a real reply.
Postal has no equivalent

The Postal backend has no message-fetch API at all — if email_backend is set to postal, this thread still runs (harmless, quietly idle every 15s) but never finds a match. The webhook door below is Postal's only real reply path.

Door 2 — the webhook

POST /email/webhook/reply exists for a real mail provider that can push replies to us directly, instead of us having to go check. It expects the token, subject, and body already figured out — it skips straight to process_reply(). It's also the fastest way to test the classification path by hand, without needing a live inbox at all — POST a fake reply body straight at it.

What process_reply() actually does

  1. Saves the reply text to email_outreach_candidate_responses.
  2. Runs it through reply_classifier.py — a list of regex patterns catches common phrasing first ("not interested", "sounds good", "count me in"...).
  3. If nothing matches, falls through to llm_reply_classifier.py (Ollama, llama3.2:3b by default), which asks the LLM to pick one of INTERESTED / NOT_INTERESTED / OTHER. The prompt explicitly tells it to look past typos and casual phrasing ("Intrested", "yess pls") rather than bailing to OTHER — a reply doesn't need to be spelled correctly to be understood.
  4. Sends an automatic "thanks for your response" confirmation email back, using wording from confirmation_content.py.
The LLM step needs a real model pulled

llm_reply_classifier.py talks to whatever Ollama instance OLLAMA_BASE_URL points at, using LLM_MODEL. If that model was never ollama pull'd, every ambiguous reply silently falls through to needs_review — no confirmation goes out, and nothing looks broken unless you check the logs for a model not found error. Confirm with docker exec <ollama-container> ollama list.

Note

Before any of that classification runs, the reply text is trimmed to cut off quoted/forwarded content — otherwise a reply that quotes our own invite underneath it could accidentally match on a word from our own email (like the word "decline" in a button label) instead of anything the candidate actually wrote.

Step 5

Auto-marking silent candidates inactive

The job nobody has to remember to run by hand.

Recall from Step 3 that every sent email gets a response deadline stamped on it. Separately, threshold_evaluator.py can be asked at any time: "which candidates are past their deadline with no reply logged at all?" It marks every one it finds as Inactive.

One route, callable from anywhere that can make an HTTP request:

TriggerHow
On demand / from a dashboardPOST /email/threshold/run
Scheduled (cron)A cron job (or any scheduler) hits the same route on a timer
Not automatic yet

Nothing in this repo currently calls this route on a timer — there's no scheduler set up. Whoever owns deployment needs to wire it into whatever cron/scheduler the project ends up using. (There used to be a standalone CLI command for this too — it was removed once every command it offered had a full HTTP equivalent with no other caller.)

Step 6

Checking on a candidate

Two read-only views into where things stand.

GET /email/status/{candidate_id} gives the current snapshot: what status the email is in right now, which round_id/ round_number they're on (see Rounds, not "purpose"), whether they've replied, and what that reply was classified as.

GET /email/status/{candidate_id}/history gives the whole timeline instead — the outreach email itself, plus every reply logged against it, oldest first. Useful for a dashboard that wants to show "here's everything that's happened with this person," not just where things stand today.

Glossary

Terms this doc uses a lot, defined once.

token

An 8-character code embedded in a sent email's subject, used as a last-resort way to match a reply back to a candidate.

candidate_id

A public identifier for a candidate across API calls — a UUID once really sent, but any string the configured candidate source can resolve (e.g. CAND-001 in testdata.json). Separate from the internal token.

round_id / round_number

Which stage of the process a candidate is on — invite, assessment, next round, or rejection — looked up from one shared rounds catalog. See Rounds, not "purpose".

backend

Whichever service actually transmits the email — Gmail (via Pub/Sub) or Postal. Swappable without touching any other code.

repository

The one file per module allowed to run database queries. Everything else goes through it instead of touching SQL directly.
